# Как усилить `simplify` для JavaScript и TypeScript

**Рекомендация:** сохранить два режима `simplify`, добавить проверку ответственности за ошибки и заменить примеры, которые меняют контракт. Языковые нюансы вынести в короткую справку, которую агент читает только для JS/TS. Скилл не менялся. Ниже предложения, а не новые правила проекта.

## Что уже умеет `simplify`

[Текущий скилл](../skills/simplify/SKILL.md) ограничивает работу диффом задачи и различает реструктуризацию и откат лишнего поведения. Он требует сохранить внешнюю валидацию, безопасность и защиту от потери данных. Крупный откат скилл только предлагает. Это полезнее, чем универсальное «удали всё подозрительное».

Скиллу не хватает двух проверок: **кто отвечает за отказ** и **какая часть контракта меняется при замене на более короткий JS/TS-код**. Он также предлагает выносить повтор из пяти строк, хотя число строк не показывает, одна ли это бизнес-политика. [Notice](../skills/simplify/NOTICE.md) указывает, что примеры и признаки взяты у Addy Osmani. Osmani, в свою очередь, ссылается на Anthropic. Это одна линия происхождения, а не три независимых подтверждения.

## Правила, которые стоит добавить

### 1. Ошибки: обрабатывай там, где это что-то даёт

1. **Удаляй `catch`, который только повторно бросает тот же объект.** Оставляй `finally` и порядок очистки. Лог, метрика, изменение причины или типа ошибки уже меняют поведение. [ESLint: `no-useless-catch`](https://eslint.org/docs/latest/rules/no-useless-catch).
2. **Оставляй обработчик там, где слой может восстановиться, перевести отказ в свой контракт или отвечает за наблюдаемость.** Если обработчик ничего из этого не делает, передай сбой слою, который может действовать. Если лог дублируется, найди владельца отчётности. Не выбрасывай полезный контекст или обязательный аудит. При обёртке сохрани исходную причину через `Error.cause`, если это поддерживает проект. [Node.js: распространение ошибок и `error.cause`](https://nodejs.org/api/errors.html#error-propagation-and-interception).
3. **Сужай `try` до операции, отказ которой умеешь обработать.** Если отсутствие необязательного файла означает «используй настройки по умолчанию», обработай `ENOENT` от `readFile`. Передай ошибки доступа, разбора и проверки дальше. Сопоставляй по документированному коду, а не по фразе из сообщения. Если общий `catch` уже возвращает настройки по умолчанию на эти ошибки, сужение меняет поведение. Это откат или исправление, не реструктуризация. [Google: Keep try blocks focused](https://google.github.io/styleguide/tsguide.html#keep-try-blocks-focused), [Node.js: `error.code`](https://nodejs.org/api/errors.html#errorcode).
4. **Не путай пропуск локального `catch` с игнорированием отказа.** Верни или ожидай Promise, если отказ должен дойти до вызывающего кода. `void promise` не обрабатывает rejection. Не удаляй `await`, если от него зависит локальный `catch`, `finally` или время освобождения ресурса. Событие `error` у `EventEmitter` и Promise rejection требуют разных путей обработки. [typescript-eslint: `return-await`](https://typescript-eslint.io/rules/return-await/), [`no-floating-promises`](https://typescript-eslint.io/rules/no-floating-promises/#ignorevoid), [Node.js: механизм ошибок API](https://nodejs.org/api/errors.html#error-propagation-and-interception).
5. **Не добавляй повтор «на всякий случай».** Для уже существующего retry выясни, какие сбои временные, можно ли безопасно повторить действие, есть ли лимит и не повторяет ли клиент сам. Удаление повтора меняет число и порядок попыток. Не добавляй обработчик процесса, который просто логирует сбой и позволяет работе продолжиться: обработчики могут менять штатное завершение процесса. [AWS Builders’ Library: повторы, идемпотентность и backoff](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/), [Node.js: `uncaughtException`](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly).

Пример: `parseConfig` разбирает JSON и проверяет схему. Только отсутствие файла означает, что можно использовать настройки по умолчанию.

```js
import { readFile } from 'node:fs/promises';

async function readOptionalConfig(path) {
  let raw;
  try {
    raw = await readFile(path, 'utf8');
  } catch (error) {
    if (error instanceof Error && 'code' in error && error.code === 'ENOENT') {
      return defaultConfig;
    }
    throw error;
  }
  return parseConfig(raw);
}
```

На временных файлах проверил пять случаев: `ENOENT` даёт дефолт, `EISDIR` и ошибки разбора и схемы доходят до вызывающего, корректный файл загружается.

### 2. JS/TS: упрощай форму, не смысл

- **Сначала ищи готовую операцию с тем же контрактом.** Проверь соседний модуль, стандартную библиотеку и уже подключённую зависимость. Сравни дефолты, ошибки, порядок и формат результата. Не объединяй код, который выглядит одинаково, но меняется по разным причинам. [Metarhia: `js-conventions`, раздел Data](https://github.com/metarhia/metaskills/blob/main/skills/js-conventions/SKILL.md#data), [Sandi Metz: The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction).
- **Короткий `map` или `filter` хорош, если точно выражает преобразование.** Для раннего выхода, нескольких эффектов или копирования растущего аккумулятора проверь, не яснее ли цикл. Spread растущего объекта в `reduce` на каждом шаге даёт квадратичное число копирований свойств в худшем случае. Перед заменой проверь пропуски в массивах, форму коллекции, порядок, мутацию и количество вызовов. [MDN: `reduce`, When to not use](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/reduce#when_to_not_use_reduce).
- **Различай отсутствие и ложное значение.** `??` подставляет значение для `null` или `undefined`, `||` для любого falsy, включая `0`, `false` и `''`. `?.` годится, когда отсутствие допустимо. Цепочка `order?.price ?? 0` не чинит нарушенный инвариант обязательной цены. [TypeScript: Truthiness narrowing](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#truthiness-narrowing), [MDN: Nullish coalescing](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Nullish_coalescing).
- **Используй вывод типов внутри модуля, если он сохраняет нужную гарантию.** Сохраняй явные типы на публичных границах, если они задают контракт или требуются проектом. Убирай generic, если он не сохраняет связи между аргументами, результатом или другими типами. `parse<T>(text): T` без runtime-проверки не доказывает, что текст содержит `T`. Для внешних данных возьми `unknown` и сузь тип существующей проверкой или схемой. Не заменяй проверку на `as`, `!` или `@ts-ignore`. `satisfies` проверяет соответствие при компиляции, а не входные данные во время выполнения. [TypeScript: generics](https://www.typescriptlang.org/docs/handbook/2/functions.html#guidelines-for-writing-good-generic-functions), [assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions), [`satisfies`](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html#the-satisfies-operator).
- **Не подменяй последовательность параллельностью.** Цикл с `await`, `Promise.all` и `Promise.allSettled` по-разному начинают работу и сообщают об ошибках. `Promise.all` не отменяет другие уже запущенные операции при первом отказе. Порядок эффектов, отмена и возможность ограничить параллелизм входят в контракт. [MDN: Async functions and execution order](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function#async_functions_and_execution_order), [MDN: Promise concurrency](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise#promise_concurrency).
- **Для React ищи второй источник истины.** Если значение полностью выводится из props и state, вычисляй его при рендере, когда это сохраняет поведение. Не удаляй эффект, который синхронизирует внешний ресурс или очищает подписку. Удаление эффекта может менять промежуточный рендер и порядок действий. [React: You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect).

### 3. Сложность: проверяй, куда она уходит

«Слоп» здесь означает наблюдаемую проблему в диффе, а не догадку об авторстве. Признаки: новая ветка без требования, обёртка без обязанности, дублированное доменное решение, заглушенный `catch`, типовое утверждение вместо проверки, комментарий без новой информации.

- **Проверка удаления.** Если убрать слой, его поведение исчезнет, вернётся в одно понятное место или размажется по вызывающим? В последнем случае слой может удерживать полезный контракт. Один потребитель не делает адаптер, транзакционную границу или тестовый шов лишними. [Matt Pocock: deletion test](https://github.com/mattpocock/skills/blob/main/docs/engineering/improve-codebase-architecture.md), [Metarhia: Wrapper](https://github.com/metarhia/metaskills/blob/main/skills/js-gof/patterns/wrapper.md).
- **Проверка общей причины.** Объединяй повторяющийся инвариант, который должен меняться в одном месте. Не объединяй похожие строки, если новые флаги заставят вызывающих угадывать разные режимы. Две ветки `switch` могут быть прозрачнее реестра обработчиков. [Sandi Metz](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction), [Fowler: Yagni](https://martinfowler.com/bliki/Yagni.html).
- **Проверка чтения.** Сколько переходов между файлами нужно, чтобы понять один сценарий? Видно ли, где он пишет данные и как завершается при ошибке? Вложенность и длина указывают, куда смотреть. Они не требуют выделять функции, если длинный линейный сценарий уже читается сверху вниз. [Google: Complexity](https://google.github.io/eng-practices/review/reviewer/looking-for.html#complexity), [Metarhia: Functions](https://github.com/metarhia/metaskills/blob/main/skills/js-conventions/SKILL.md#functions).

## Где текущие примеры меняют поведение

| Пример в `simplify` | Что меняется | Как исправить пример |
| --- | --- | --- |
| `reduce` с объектом `{ id: { count } }` → `Map<string, number>` | Форма результата, доступ по ключу, порядок перечисления и сериализация. Для массива с пропусками меняется и обход. | Использовать локальный аккумулятор с той же формой и тем же обходом. Описывать смену коллекции отдельно, если представление видят вызывающие. |
| `async function` с `return await` → обычная функция | Синхронное исключение больше не превращается в rejection. Даже без исключения меняется идентичность Promise, а в некоторых сценариях время продолжения и стек. | Вместо общего примера «лишнего async» показать удаление `catch (error) { throw error; }`. Сохранить `async`, `await` и `finally`, если он есть. |
| `for...of` + `push` → `.filter()` | `filter` пропускает дырки, а итератор массива отдаёт `undefined` для дырки без унаследованного свойства. Цикл также принимает произвольный iterable. | Сказать, что это преобразование обычного плотного массива с чистым предикатом. Оставить цикл, если отличаются обход или эффекты. |
| `if (user.nickname) …` → `user.nickname || user.fullName` | На истинной ветке исходник читает `nickname` дважды, новый код один раз. На обычном объекте со стабильными полями совпадает. Для getter совпадение не гарантировано. | Использовать уже прочитанное локальное значение в обеих версиях. Отдельно указать, считается ли пустая строка отсутствием. |
| `JSON.stringify(internalConfig)` объявлен безопасным, потому что объект внутренний | Внутренний объект может содержать цикл или `BigInt`. Неожиданный сбой не становится невозможным из-за места создания объекта. | Если `{}` маскирует ошибку сериализации, назвать удаление fallback изменением поведения. Для примера отката указать, почему потребители не должны получать `{}` и куда должна дойти ошибка. |

**Проверка:** на Node.js `v26.13.0` запустил проверки для синхронного исключения, rejection, идентичности Promise, локального `catch` и порядка `finally`. Проверил обе формы результата `reduce`/`Map`, массив с пропуском, чтение getter, `||`/`??` и ошибки `JSON.stringify` на цикле и `BigInt`. Все проверки подтвердили описанные различия. Это проверки семантики, не замер производительности и не прогон скилла.

## Что говорят эмпирические исследования

- **TypeScript, Lee и соавторы, MSR 2026.** В отфильтрованной выборке связанных с типами PR среднее число добавлений `any` на PR составило `2.16` у агентов и `0.24` у людей. Выборку выделяли регулярками и LLM-классификатором. Это сравнение числа добавлений в конкретной выборке, а не оценка вероятности бага в произвольном TypeScript PR. Оно подкрепляет отдельный поиск обходов проверки типов. [Статья, метод и результаты](https://arxiv.org/html/2602.17955v2).
- **Python, Huang и соавторы, MSR 2026.** На `crewAI` агентские PR получили более высокий показатель семантического дублирования. Авторы измеряли близость функций по эмбеддингам в одном репозитории. Это повод искать повтор уже существующей логики до извлечения новой абстракции, но не прямое измерение дублирования в JS/TS. [Статья, §§ 2–3 и 6](https://arxiv.org/html/2601.21276#S2).
- **Внедрение Cursor, He и соавторы, MSR 2026.** Сравнение репозиториев с подобранной контрольной группой показало рост предупреждений статического анализа и сложности после внедрения Cursor. Измерение шло на уровне проекта. Оно не позволяет приписать конкретную строку агенту. [Статья](https://arxiv.org/abs/2511.04427).
- **Сопровождение Java, Borg и соавторы, 2026.** В двухфазном эксперименте с 151 участником авторы не нашли значимого различия в скорости и качестве, когда другие разработчики развивали решения без AI. Задачи и время наблюдения были ограничены. Результат не поддерживает универсальный вывод о том, что код с AI-помощью хуже сопровождать. [Статья](https://link.springer.com/article/10.1007/s10664-026-10889-1).

## Порядок обновления скилла

1. **Сначала исправить примеры.** Заменить небезопасные `async` и `reduce` примеры. Показать парой случаев полезный узкий `catch` и бесполезный повторный `throw`. Убрать автоматическое правило про пять строк.
2. **Добавить в ядро критерий решения.** Назвать требование, вызывающий код или механизм отказа. Проверить, владеет ли текущий слой решением. Выбрать реструктуризацию, доказанный локальный откат или предложение без правки. Если нельзя установить контракт, оставить код и назвать, чего не хватает.
3. **JS/TS-детали загрузить по условию.** Справка нужна при работе с `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx` и `.d.ts`. В ней разместить async, обработку ошибок, narrowing, коллекции и условный раздел для React. Не добавлять новый отдельный скилл и не заводить второй стайлгайд.
4. **Проверить поведение агента на парных сценариях.** Metarhia [держит сценарии eval рядом со скиллами](https://github.com/metarhia/metaskills/blob/main/evals/cases.js). Взять идею коротких сценариев, но оценивать контракт результата, а не наличие `for`, `await` или `**` в исходнике.

| Сценарий для проверки агента | Ожидаемое решение |
| --- | --- |
| Локальный `catch` только перебрасывает ошибку. Есть `finally` с освобождением ресурса. | Удаляет `catch`. Сохраняет объект ошибки и порядок освобождения. |
| Необязательный файл отсутствует. В других случаях чтение или разбор падают. | Дефолт только при ожидаемом `ENOENT`. Не превращает ошибки доступа или повреждённый файл в успех. |
| Пограничный JSON проверяется схемой. Внутренние вызовы уже получают проверенный тип. | Сохраняет схему. Убирает только доказанно повторную проверку, если её поведение не часть контракта. |
| Транзитная обёртка и адаптер с одной реализацией. | Предлагает удалить первую, если её контракт не наблюдаем. Сохраняет второй, если он переводит сторонний контракт. |
| Значение `0` допустимо. Коллекция результата сериализуется как объект. | Не заменяет `??` на `||` и не возвращает `Map` вместо объекта. |
| Ясный код без подтверждённых кандидатов. | Оставляет дифф без изменений. |
