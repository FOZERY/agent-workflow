# Гайд по скиллам

[Обзор](README.ru.md) · [Маршруты](FLOW.ru.md) · [English version](GUIDE.md)

Гайд описывает скиллы в порядке процесса: настроить, понять, обсудить, спланировать, реализовать, улучшить, писать. У каждого скилла сказано, что он делает, кто его запускает и что ты получаешь, и есть пример запроса.

Команда с `/` работает в Claude Code. В Codex вместо `/` пиши `$`. Скилл с пометкой «агент может запустить сам» сработает и без команды, если твоя просьба подходит под его описание.

## Настроить

### `/setup-workflow`

Настраивает процесс для проекта. Спрашивает про правила, проверки, права, доставку в Git, источники фактов и агентов для каждого шага. Потом предлагает скиллы, ставит одобренные и пишет корневой `AGENTS.md`: общий блок правил и по секции на каждый скилл. Запускай снова, когда правила меняются или вышла новая версия набора.

```text
/setup-workflow
```

### `/setup-home-repo`

Делает домашний репозиторий для проекта из нескольких репозиториев. В доме лежат навигация, общие материалы и точки входа для клиентов. Код и правила дочерних репозиториев остаются на месте. Если дому нужны правила процесса, потом запусти в нём `/setup-workflow`.

```text
/setup-home-repo приложение лежит в ../web, ../api и ../infra
```

### `/ask-workflow`

Отвечает на вопрос о процессе и советует следующий скилл с командой для запуска. Читает `AGENTS.md` проекта и установленные скиллы. Сам ничего не запускает.

```text
/ask-workflow у меня баг в GitHub issue #42, с чего начать?
```

## Понять

### `/investigate`

Изучает задачу до обсуждения. Два исследователя читают историю задачи (тикеты, коммиты, merge requests, вики, чаты, логи, как настроено в setup) и код вокруг неё. Для задачи скилл сохраняет факты со ссылками на источники в `facts.md` рядом с задачей. Для вопроса без задачи файл сохраняется, только если ты попросишь. Потом скилл объясняет тебе задачу простыми словами, со схемами там, где они помогают. Потом `implement` передаёт этот файл исполнителям.

```text
/investigate JIRA-1234
/investigate как отправляются напоминания об уроках?
```

### `/recall`

Восстанавливает, где остановилась недавняя работа по теме. Читает `CONTEXT.md`, недавние журналы сессий проекта, а для названной фичи или бага ещё и общую историю: трекер, merge requests и другие источники из настроек `investigate`. Сверяет каждую ветку, PR и тикет с текущим состоянием и выдаёт короткую сводку: суть, линии работы со статусами, повторяющиеся проблемы и следующий шаг. Ничего не меняет.

```text
/recall
/recall работа над экспортом на прошлой неделе
```

### `research`

Отвечает на вопрос по первоисточникам: официальной документации, спецификациям, исходному коду. Сохраняет отчёт со ссылками в репозитории. Подходит для фактов за пределами проекта. Агент может запустить сам.

```text
Исследуй, как Telegram-бот создаёт темы в личке. Со ссылками на Bot API.
```

## Обсудить

### `grilling`

Задаёт тебе вопросы раунд за раундом, пока не приняты все решения по идее. К каждому вопросу даёт рекомендуемый ответ. Факты ищет сам, у тебя спрашивает только решения. Агент может запустить сам.

```text
Погриль меня по плану: перевести уведомления на очередь.
```

### `/grill-with-docs`

Тот же опрос, что `grilling`. Попутно записывает новые термины в `GLOSSARY.md` и предлагает ADR для решения, которое трудно отменить.

```text
/grill-with-docs модель расчётного периода
```

### `domain-modeling`

Следит, чтобы у каждого понятия было одно имя в `GLOSSARY.md`, и записывает трудно отменяемые решения в ADR. Спорит с термином, который расходится с глоссарием, и сверяет утверждения с кодом. Агент запускает его сам, когда разговор идёт о терминах или решениях.

```text
«Групповой урок» это урок или серия уроков? Обнови глоссарий.
```

### `prototype`

Делает временный код, чтобы ответить на вопрос о дизайне. Для логики это один HTML-файл, который прогоняет модель состояний через трудные случаи. Для интерфейса это несколько вариантов на одной странице с переключателем. В настоящий код идёт решение, а не прототип. Агент может запустить сам.

```text
Сделай прототип переходов статуса урока: отмена, перенос, возврат.
```

### `draw-diagram`

Предлагает схему, когда картинка объяснит дизайн лучше слов. После твоего согласия отдельный агент рисует редактируемый файл Excalidraw и PNG. Агент может запустить сам.

```text
Нарисуй, как задача идёт от трекера до смерженного PR.
```

## Спланировать

### `/to-plan`

Сохраняет план реализации одной задачи рядом с задачей: подход, шаги, проверки, открытые решения. Спецификация и тикеты не нужны. План остаётся в статусе `Proposed`, пока ты его не одобришь, а одобрение не запускает работу.

```text
/to-plan JIRA-1234
```

### `/to-spec`

Превращает обсуждение или законченную карту `wayfinder` в спецификацию. Сверяет с тобой швы для тестов, показывает черновик и публикует в трекер после твоего одобрения.

```text
/to-spec
```

### `/to-tickets`

Режет план, спецификацию или обсуждение на тонкие тикеты, у каждого указаны блокирующие тикеты. Перед публикацией показывает набор на одобрение.

```text
/to-tickets по .docs/billing/plan.md
```

### `/wayfinder`

Раскладывает работу, которая слишком большая и неясная для одной сессии. Создаёт тикет-карту и тикеты-решения и закрывает их по одному. Когда карта готова, советует `to-spec` или `to-plan`.

```text
/wayfinder переезд с SQLite на Postgres
```

## Реализовать

### `implement`

Реализует согласованную задачу. Сессия становится оркестратором:

1. Читает задачу, план или тикеты и файл фактов от `investigate`, если он есть.
2. Выбирает размер: тривиально (правит и останавливается), мелко (пишет сам), обычно (один исполнитель) или крупно (несколько исполнителей).
3. Один раз просит подтвердить режим, шаги и швы для тестов. Для простой задачи шаги можно отключить.
4. Исполнители пишут код в отдельных сессиях по `implement/WORKER.md`: тесты, упрощение, полный прогон тестов, ревью по стандартам (Standards).
5. Если исполнителей несколько, сводит их части в одно дерево.
6. На этом дереве сверяет результат с задачей (ревью Spec), а потом проверяет изменённое поведение через `verify`, если он включён. Потом коммитит, если можно, и отчитывается с доказательствами.

Агент запускает его сам, когда ты просишь что-то изменить.

```text
Реализуй JIRA-1234 по плану из .docs/jira-1234/plan.md.
```

### `tdd`

Сначала тест: один падающий тест, потом минимальный код, который его проходит. Тесты идут через публичные интерфейсы на швах, которые ты подтвердил. Для бага первый тест воспроизводит его и должен упасть по той самой причине. Если тест вышел бы хрупким или медленным или нечем независимо проверить результат, скилл берёт ближайшую исполняемую проверку и говорит об этом. Ещё умеет проверить существующие тесты и убрать те, что ничего не доказывают. `implement` запускает его, если так задано в настройках проекта. Агент может запустить сам.

```text
Добавь правило про просроченное домашнее задание через тест.
Проверь тесты в src/billing и убери те, что ничего не доказывают.
```

### `simplify-codebase`

Находит, что упростить в изменённом коде: глубокую вложенность, неясные имена, повторы, ненужные проверки и абстракции. Субагент-искатель составляет список находок, а сессия, которая писала код, применяет их по одной с прогоном тестов. Крупные удаления приходят тебе как предложения. `implement` запускает его, если так задано в настройках проекта. Агент может запустить сам.

```text
Упрости то, что мы поменяли в этой ветке.
```

### `verify`

Проверяет, что изменение работает в запущенном продукте, а не только в тестах. Способ проверки вы выбираете в `setup-workflow`: локально с тестовыми данными, полным e2e-путём, в тестовом неймспейсе через `kubectl` и браузер или раскаткой на стейдж. Что проверять, берётся из задачи: скилл выписывает поведение из критериев приёмки, ты подтверждаешь список и действия, которым нужно одобрение, и он отчитывается по каждому пункту с доказательствами. `implement` запускает его, если так задано в настройках проекта. Агент может запустить сам.

```text
Проверь отмену урока в тестовом неймспейсе.
```

### `code-review`

Проверяет изменения по двум осям: Standards (правила кода проекта) и Spec (делает ли код то, что просила задача). Каждая ось идёт в свежем субагенте. В `implement` ось Standards проверяет каждый исполнитель, а Spec проверяет оркестратор. Агент может запустить сам.

```text
Проверь эту ветку относительно main.
```

## Улучшить

### `/retro`

Читает недавние сессии (их журналы, `CONTEXT.md`, `LESSONS.md` и историю Git) и находит ошибки, которые нашли и исправили. Каждый долгоживущий урок превращает в инструкцию: правило в скилле, новый скилл, правило проекта или урок. Правит только то, что ты одобрил, и записывает ретро в `CONTEXT.md`. Для правки ядра или настроек скилла даёт тебе команду `/setup-workflow`.

```text
/retro
/retro последние две недели, работа над биллингом
```

### `/refactor-codebase`

После этапа работы находит, где структура кода мешает его менять: неглубокие модули, нарушенные правила проекта, плохие практики стека. Заодно собирает, что упростить, но пока ничего не меняет. Ты выбираешь кандидата или упрощения, обсуждаешь его через `grilling`, а `implement` переписывает его с сохранением поведения.

```text
/refactor-codebase начиная с тега v0.3
```

### `/refactor-docs`

Делает документы и память проекта понятнее по тексту и структуре. Сохраняет каждое решение, требование и факт и сверяет результат с оригиналом.

```text
/refactor-docs docs/architecture.md
```

### `/cleanup-artifacts`

Разбирает устаревшие рабочие файлы: заметки, планы, отчёты, схемы. Показывает план с доказательствами по каждому файлу. Переносит в Корзину или архив только одобренные тобой файлы и оставляет карту восстановления.

```text
/cleanup-artifacts только ревью
```

## Писать

### `writing-for-people`

Правила для ответов и объяснений: результат первым, простые слова, один факт на предложение, без машинных привычек. Нумерованный список привычек с примерами, на английском и русском. Сошлись на него из своих инструкций, чтобы агент читал его перед первым ответом.

### `writing-technical`

Правила для технических документов, скиллов, `AGENTS.md`, спецификаций и тикетов на основе контролируемого английского ASD-STE100: одна мысль на предложение, условие перед действием, настоящие имена, нумерованные шаги. Есть русская версия правил.

### `writing-for-agents`

Порядок написания скилла или `AGENTS.md`: найти работу, выбрать, кто запускает, написать frontmatter и тело, вычистить каждое предложение, которое не меняет поведение агента, проверить ссылки и прогнать скилл на свежем агенте. Стиль предложений берётся из `writing-technical`.

### `/rephrase`

Пересказывает последний ответ простыми словами. Сохраняет все факты и решения.

```text
/rephrase
```
