# Triage

Read root `AGENTS.md` and its mandatory triage procedure before evaluating work. The project defines request sources, routing, evidence of current relevance, overlap/duplicate criteria, states, approval gates and permitted operations. Missing evidence or policy remains an explicit gap; agree the affected decision instead of forcing a tracker state.

Issues, incidents and incoming PRs/MRs are request surfaces only where the project includes them. Resolve references according to its sources, not a presumed GitHub issue number. Presentation-only triage is valid when systems are read-only.

Use the project's provenance, language and AI-disclosure requirements for any proposed or authorized publication. Preparing text is not permission to post it.

## Defaults

Use these when the project instructions settle nothing for triage, and mention once that `setup-agents-workflow` can configure the project. Every comment, label, assignment or state change still needs the user's confirmation.

- **Request surface:** open issues and PRs/MRs of the current repository's tracker, read through its CLI (`gh` or `glab`). Include PRs/MRs only from authors outside the repository's collaborators; a PR the user names is always in scope.
- **Needs attention:** three groups, oldest first: unlabeled items; items in `needs-triage`; `needs-info` items with reporter activity since the last triage note. Show counts and a one-line summary per item, then let the user pick.
- **AI disclosure:** start every comment the agent drafts with `> *This was generated by AI during triage.*`

## Roles

The following upstream vocabulary is a reference for projects that adopt it, not a mandatory state machine. Follow the project's own categories, states and mappings; create no labels merely to match this list.

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

For a PR/MR, map readiness against the attached change and the project's acceptance procedure. A brief can establish the remaining work; neither that brief nor a readiness state authorizes execution or merge.

Use the project's required classification and transition rules. Conflicting states or ownership go to the responsible person before mutation; useful read-only investigation can continue within scope.

A readiness state describes eligibility, not execution authority. Assignment, an available worker or an incoming PR does not bypass project start, acceptance or merge rules.

## Invocation

Interpret the maintainer's requested scope and distinguish inspection, recommendation and mutation. Natural-language commands identify desired outcomes but still follow applicable authority and evidence rules.

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the project's agreed request surfaces and attention criteria. Show relevant unresolved work, owner/assignee, current status and source links, including recent activity that requires re-evaluation. Use the project's order and categories; without them, use the [default groups](#defaults).

Include incoming PRs/MRs only under its configured scope and ownership rules. Present concise summaries and let the user select work where human selection is required; do not mix another collaborator's active delivery work into incident triage without a reason.

## Triage a specific issue or PR

1. **Gather context.** Read the request and its discussion, authoritative requirements/runbooks, relevant domain decisions and available release/system evidence. Establish affected subsystem, environment, version/time range and responsible team. Preserve the distinction between reported behavior, observed facts and hypotheses.

2. **Check current and overlapping work.** Search linked and active tasks, relevant assignees/teams and recent completed work using the project's criteria. Compare behavior, affected scope and deployment, not just wording. An existing implementation or fix ticket does not establish that the incident is resolved; merged code may not be deployed. Search the codebase for an existing implementation of the requested behavior by its domain concept, not only the request's wording, and report where you looked. Identify duplicate evidence and missing coverage before recommending new work. Surface applicable prior rejection records from the configured source without treating them as automatic decisions.

3. **Verify within authority.** Use available reporter evidence, tests, logs and release information. Respect already established results; perform additional reproduction or PR checkout/checks only when needed and allowed in the agreed environment/working copy. Do not run unsafe production experiments or replace another worker's state. Failure to reproduce is inconclusive without further grounds; unavailable evidence is a limit, not a resolution.

4. **Recommend.** Present affected scope and owner, evidence and its limits, related/in-progress work, recommended disposition and the information or approval still needed. Distinguish an active incident, mitigation, delivered resolution, duplicate, deferral and rejection where the project uses those outcomes. Follow its decision thresholds and escalate ambiguity to the responsible person.

5. **Clarify if needed.** Use `grilling` and `domain-modeling` when a decision actually needs discussion. Their document writes follow project permissions; triage does not automatically generate or update a glossary, ADR or specification.

6. **Apply only authorized outcomes.** At the required human checkpoint, obtain the decision or reuse its explicit existing approval. Link, comment, route, label, assign, transition or close only as the project permits. Use [agent-brief guidance](references/AGENT-BRIEF.md) when a brief is requested or required, and [rejection-record guidance](references/OUT-OF-SCOPE.md) when a durable rejection belongs in the project's history. With read-only access, return the proposed outcome for its owner; do not publish, invent a closure or create parallel implementation.

## Quick state override

For a requested state override, identify the exact permitted transition and its effects. Reuse explicit authorization for that operation; ask about unclear scope or missing authority rather than re-running a whole interview. Keep any project-required evidence/approval gate and distinguish readiness from permission to start. A brief is required only by the project procedure or the user's request.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

Read relevant prior notes and current source state, check whether open questions were answered, and present the updated picture. Preserve confirmed findings and avoid re-asking settled questions; new evidence may require re-evaluation rather than silently overwriting history.

**Done when:** the requested evaluation has a sourced conclusion or explicit evidence gap, related work and ownership are accounted for, and each proposed/authorized action is clearly distinguished from what actually happened.
